# Gemini Instructions

Read every Markdown file inside the /docs folder before making any changes.

Treat the documentation as the source of truth.

Do not invent business rules.

Do not remove existing functionality without approval.

If documentation conflicts, stop and explain the conflict instead of guessing.

Keep business logic out of routes and templates.

Prefer service classes.

Prefer reusable code.

Build one implementation phase at a time.

After completing each phase:

- Explain what changed.
- List affected files.
- Suggest tests.
- Wait for approval before starting the next phase.

If a requirement is unclear, ask instead of assuming.
